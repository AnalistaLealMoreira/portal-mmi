Guia de implantação em servidor

Versão de 01/10/2026 · Laravel 13 / PHP 8.4 · Repositório AnalistaLealMoreira/portal-mmi

1.Visão geral

O Portal MMI é uma aplicação Laravel 13 / PHP 8.4 que dá acesso controlado aos relatórios de Power BI da MMI Incorporações. Ela substitui a versão em Django e usa o mesmo banco SQL Server (portalmmi), sem migração de dados.

  • Código-fonte: github.com/AnalistaLealMoreira/portal-mmi, branch main.
  • Banco: SQL Server automate.leal.local, banco portalmmi. As tabelas são as mesmas do Django e as senhas usam o mesmo formato (pbkdf2_sha256), então os usuários entram com as senhas que já tinham.
  • Sessão e cache: em arquivo, na pasta storage/. Não há Redis, fila nem tabela extra no banco.
  • Front-end: Bootstrap 5, Bootstrap Icons, Chart.js e a fonte Inter, carregados de CDN (cdn.jsdelivr.net e fonts.googleapis.com). Não é preciso Node.js nem build de front-end.
  • Relatórios: cada link de BI abre num iframe dentro do portal. Todo acesso fica registrado na tabela auditoria_acessolog.

2.Requisitos do servidor

O servidor precisa de PHP 8.3 ou superior com as extensões de SQL Server e de acesso à porta 1433 do banco. A aplicação foi desenvolvida e testada com PHP 8.4.26 NTS x64 no Windows Server 2019.

3.Banco de dados

Não é preciso criar nem migrar nada: o portal Laravel usa as tabelas que o Django já criou no banco portalmmi. Basta um login SQL com leitura e escrita.

TabelaConteúdo
accounts_usuarioUsuários, papéis e senhas (pbkdf2_sha256)
accounts_redepermitidaRedes (CIDR) de onde usuários normais podem acessar
empresas_empresaEmpresas
setores_setorSetores de cada empresa
funcionarios_funcionarioVínculo usuário → empresa e setor
funcionarios_funcionario_links_liberadosLinks liberados para cada funcionário
bi_links_linkbiLinks dos relatórios de BI
auditoria_acessologRegistro de cada acesso a relatório

Permissões do login da aplicação: apenas db_datareader e db_datawriter no banco portalmmi. O login usado até hoje pelo portal Django (pbi) serve; quem define é o DBA.

USE portalmmi;
CREATE USER [pbi] FOR LOGIN [pbi];   -- se o usuário ainda não existir no banco
ALTER ROLE db_datareader ADD MEMBER [pbi];
ALTER ROLE db_datawriter ADD MEMBER [pbi];

Migração: opcional. php artisan migrate só cria as tabelas que ainda não existem; num banco vindo do Django, cria apenas a tabela de controle migrations. Se for rodar, use uma conta com permissão de DDL; no dia a dia, o login da aplicação não precisa dela.

Datas: gravadas em UTC (como no Django) e exibidas no fuso America/Sao_Paulo.

Convive com o Django: os dois portais podem usar o mesmo banco ao mesmo tempo durante a transição. Um usuário criado ou com a senha trocada em um deles entra no outro com a mesma senha.

Antes de colocar no ar: faça um backup completo do banco portalmmi. As exclusões pelo portal são em cascata (setor, usuário e link) e apagam também o histórico de auditoria ligado a eles.

4.Instalação passo a passo

Os comandos abaixo são para PowerShell no Windows Server, instalando em C:\inetpub\portal-mmi. Ajuste o caminho se for outro.

  1. Clonar o repositório 
    cd C:\inetpub
git clone https://github.com/AnalistaLealMoreira/portal-mmi.git
cd portal-mmi
  2. Instalar as dependências PHP (sem os pacotes de desenvolvimento) 
    composer install --no-dev --optimize-autoloader
  3. Criar o .env a partir do modelo e preencher as variáveis de produção (seção 5) 
    Copy-Item .env.example .env
notepad .env
  4. Gerar a chave da aplicação. Rode uma única vez: trocar a chave depois derruba todas as sessões abertas. 
    php artisan key:generate
  5. Testar a conexão com o banco 
    php artisan about
php artisan db:show

    O db:show deve listar as tabelas do portal (accounts_usuario, bi_links_linkbi etc.).

  6. Gerar os caches de produção 
    php artisan config:cache
php artisan route:cache
php artisan view:cache

    Depois de qualquer mudança no .env, rode php artisan config:cache de novo: com o cache ativo, o .env não é relido.

  7. Dar permissão de escrita ao usuário do pool do IIS em storage e bootstrap\cache (sessões, cache, views compiladas e logs ficam ali) 
    icacls storage /grant "IIS AppPool\PortalMMI:(OI)(CI)M" /T
icacls bootstrap\cache /grant "IIS AppPool\PortalMMI:(OI)(CI)M" /T

    O restante do projeto precisa só de leitura. O .env não deve ficar legível para outros usuários do servidor.

  8. Configurar o site no servidor web, apontando para a pasta public (seção 6).
  9. Criar o primeiro administrador, apenas se o banco for novo. No banco atual os usuários do Django já existem. 
    php artisan portal:criar-admin admin --email=admin@mmi.com.br

    O comando pede a senha e a confirmação no terminal.

Nunca use php artisan serve em produção: ele é um servidor de desenvolvimento, de um processo só.

6.Servidor web

A raiz do site deve ser a pasta public, nunca a raiz do projeto: só assim o .env, o código e os logs ficam fora do alcance do navegador. Todas as requisições que não sejam arquivos de public vão para public\index.php.

IIS (Windows Server)

  1. Instale o IIS com o recurso CGI (Server Manager → Web Server → Application Development → CGI) e o módulo URL Rewrite 2.1.
  2. Em Handler Mappings, registre o PHP via FastCGI: *.php → FastCgiModule → C:\php\php-cgi.exe. Se preferir, use o PHP Manager for IIS.
  3. Crie um Application Pool PortalMMI (.NET CLR: No Managed Code, Pipeline: Integrated).
  4. Crie o site apontando o Physical path para C:\inetpub\portal-mmi\public, no pool PortalMMI, com binding HTTPS (porta 443) e o certificado do domínio.
  5. O arquivo public\web.config já vem no repositório, com o conteúdo abaixo. Ele faz no IIS o mesmo que o .htaccess faz no Apache.
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
  <system.webServer>
    <defaultDocument>
      <files>
        <clear />
        <add value="index.php" />
      </files>
    </defaultDocument>
    <directoryBrowse enabled="false" />
    <rewrite>
      <rules>
        <rule name="Remove barra final" stopProcessing="true">
          <match url="^(.*)/$" />
          <conditions>
            <add input="{REQUEST_FILENAME}" matchType="IsDirectory" negate="true" />
          </conditions>
          <action type="Redirect" redirectType="Permanent" url="/{R:1}" />
        </rule>
        <rule name="Laravel" stopProcessing="true">
          <match url="^" ignoreCase="false" />
          <conditions logicalGrouping="MatchAll">
            <add input="{REQUEST_FILENAME}" matchType="IsDirectory" negate="true" />
            <add input="{REQUEST_FILENAME}" matchType="IsFile" negate="true" />
          </conditions>
          <action type="Rewrite" url="index.php" appendQueryString="true" />
        </rule>
      </rules>
    </rewrite>
    <httpErrors existingResponse="PassThrough" />
  </system.webServer>
</configuration>

No php.ini usado pelo IIS, confira: extension=pdo_sqlsrv e extension=sqlsrv ativas, cgi.fix_pathinfo=1, fastcgi.impersonate=1 e date.timezone=UTC.

Apache ou Nginx (Linux)

  • Apache: DocumentRoot na pasta public, com AllowOverride All e mod_rewrite ativo. O public/.htaccess já está no repositório.
  • Nginx + PHP-FPM: root na pasta public, com try_files $uri $uri/ /index.php?$query_string; e o bloco location ~ \.php$ apontando para o PHP-FPM.

HTTPS, HSTS e proxy reverso

  • Com PORTAL_FORCE_HTTPS=true, o portal redireciona HTTP para HTTPS e envia Strict-Transport-Security com includeSubDomains; preload. O navegador passa a exigir HTTPS em todos os subdomínios por 1 ano. Se algum subdomínio ainda usa HTTP, avise antes de ligar.
  • Se o HTTPS terminar num proxy reverso ou balanceador (e não no próprio IIS), o portal enxerga a requisição como HTTP e entra em loop de redirecionamento. Nesse caso é preciso ajustar o código para confiar no proxy (trustProxies em bootstrap/app.php, só para o IP do proxy). Avise o desenvolvimento antes.
  • O bloqueio por rede dos usuários normais usa o IP de origem (REMOTE_ADDR). Atrás de um proxy, todos chegariam com o IP do proxy; o mesmo ajuste de trustProxies resolve. Nunca confie em X-Forwarded-For vindo direto da internet.

Relatórios no iframe

O portal envia X-Frame-Options: DENY, então ele próprio não pode ser embutido em outro site. Os relatórios do Power BI são abertos dentro do portal, então o navegador do usuário precisa alcançar app.powerbi.com e o domínio de cada link cadastrado.

7.Validação após a implantação

Com o site no ar, entre com um usuário Administrador já existente e passe pela lista abaixo. Use registros de teste nos cadastros: o banco é o de produção. As marcações desta página não são salvas.

Infraestrutura

  • php -m lista pdo_sqlsrv e sqlsrv
  • php artisan about mostra Environment: production, Debug Mode: OFF e os caches de config, rotas e views ativos
  • https://<domínio>/up responde 200 (verificação de saúde do Laravel, útil para monitoramento)
  • http://<domínio> redireciona para https://
  • https://<domínio>/.env e https://<domínio>/composer.json não são acessíveis
  • O pool do IIS consegue gravar em storage\logs (aparece o arquivo laravel-AAAA-MM-DD.log após o primeiro erro ou aviso)

Aplicação

  • Login com nome de usuário e com e-mail, usando uma senha que já existia no Django
  • "Manter conectado" desmarcado: a sessão acaba ao fechar o navegador
  • Cadastro, edição e exclusão de empresa, setor, usuário e link de BI (com registros de teste)
  • Abrir um relatório: o Power BI carrega no iframe e a marca d'água LGPD aparece para usuários Normal e Especial
  • O acesso aparece em Auditoria, com usuário, data/hora (horário de Brasília) e IP real do usuário
  • Usuário Normal fora de uma rede permitida vê "Acesso restrito à rede da empresa"; dentro dela, entra
  • Diretor, Admin da Empresa e Usuário Especial entram de qualquer rede
  • O painel (Visão geral) mostra os gráficos e a tela Relatórios mostra os cards

8.Atualizações e operação

Publicar uma nova versão

cd C:\inetpub\portal-mmi
php artisan down                       # página de manutenção (503)
git pull origin main
composer install --no-dev --optimize-autoloader
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan up

Anote o commit em produção antes do git pull (git rev-parse --short HEAD): é ele que se usa para voltar atrás.

Voltar à versão anterior

cd C:\inetpub\portal-mmi
php artisan down
git checkout <commit-anterior>
composer install --no-dev --optimize-autoloader
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan up

Como o portal não altera a estrutura do banco, voltar o código basta: não há migração para desfazer. Para voltar a seguir o main depois, rode git checkout main.
